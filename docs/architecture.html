Why Strands Agents SDK (Not LangGraph)

Key advantages of Strands for MailPilot:
  • 80% less boilerplate â€” Each agent is literally: model + prompt + tools. No graph definition, no state schema, no edge routing.
  • Model-driven approach â€” The LLM decides when to call tools and what to do next. We don't manually code the logic flow â€” the AI handles it.
  • Direct tool calling â€” The @tool decorator auto-generates the JSON schema from the function signature and docstring. LangGraph needs manual schema definition or Pydantic models.
  • Simple multi-agent â€” Our orchestrator just calls classify(email), then extract(email), then briefing(). No subgraph nesting, no state channel merging.
  • One dependency â€” strands-agents includes everything (model providers, tools, agent loop). LangGraph requires 4-5 separate packages.
  • OpenAI-compatible endpoint â€” We just pass base_url and it works with any endpoint. No provider-specific wrappers needed.
  • Production-ready out of the box â€” Built-in observability (OpenTelemetry), streaming, retry, and tool execution. LangGraph needs LangSmith, custom callbacks, etc.
When would LangGraph be better?
  • Complex cyclic workflows where agents loop back to each other based on conditions
  • Human-in-the-loop approval steps with state persistence
  • Long-running workflows that need checkpoint/resume
  • When you need explicit control over every decision branch

For MailPilot: Our pipeline is linear (classify â†’ extract â†’ store â†’ brief). Strands' simplicity is a perfect fit. We'd be fighting LangGraph's complexity for no benefit.
